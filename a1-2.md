# Test ideas: secure document upload

## Functionality

**Formats**
- Upload a valid PDF, DOCX and TXT. Each should succeed and open correctly afterwards.
- Upload unsupported formats (.exe, .zip, .jpg, .doc, .rtf, .xlsx) and expect a clear rejection message.
- Upload files with an uppercase extension (`.PDF`), double extensions (`contract.pdf.exe`) and no extension.
- Upload a file whose extension and content disagree (a PNG renamed `.pdf`, a ZIP renamed `.docx`). Does the system check content or only the extension?
- Upload variants: password-protected PDF, PDF with embedded files or forms, DOCX with macros (.docm renamed), empty TXT, TXT in UTF-8, UTF-16 and ANSI, and TXT with Thai or other non-Latin text.
- Upload a legacy .doc, and DOCX files produced by Word, LibreOffice and Google Docs.

**Size limit (boundaries)**
- Test 0 bytes, 1 byte, 20MB − 1 byte, exactly 20MB, 20MB + 1 byte and a very large file (1GB+).
- Clarify whether "20MB" means 20,000,000 or 20,971,520 bytes, and test both sides of that ambiguity.
- Check whether the limit is enforced on the client only. Bypass the UI and send a 25MB file via API or cURL.
- Send a request with a falsified `Content-Length` header.

**Progress feedback**
- Check the progress indicator advances monotonically from 0% to 100%, and that it doesn't show 100% before the server has confirmed storage.
- Test with small files (the bar may never render), large files and a throttled network.
- Cancel mid-upload and check the state is clean, with no partial file visible.
- Lose connectivity mid-upload, then reconnect, and check for retry or resume behaviour and a meaningful error.
- Close the tab, refresh the page or let the session expire mid-upload.
- Upload several files at once, and the same file twice in quick succession (double-click, double-submit).

**Naming and metadata**
- Test long filenames (255+ characters), special characters (`&`, `#`, `%`, quotes, emoji, spaces), Unicode, and names with leading dots.
- Upload two files with the same name, and check the behaviour is defined (overwrite, version or rename).
- Check metadata (uploader, timestamp, size, type) is shown correctly.

**Auditing**
- A successful upload creates an audit record with the user, filename, size, timestamp and result.
- Failed uploads (wrong type, too large, network failure, virus detected, server error) also create a record with the failure reason.
- Cancelled and partially completed uploads are recorded accurately.
- If the audit service is down, check whether the upload fails safely or succeeds without a record.
- Check the audit entry is created exactly once, with no duplicates on retry and none missing on rapid uploads.

## Data Integrity

- Compare a SHA-256 hash of the file before upload and after download. They must match byte for byte.
- Open the downloaded PDF, DOCX and TXT and check there is no corruption, truncation or encoding change (line endings, BOM, special characters).
- Interrupt the upload at several points (kill the network, restart the server, fill the disk). There should be no orphaned or half-written file, and no metadata record without a file or file without a record.
- Check the file and its database record stay consistent after a failed transaction, and that the status shown to the user matches the stored reality.
- Upload the same file concurrently from two users and check files are not mixed up or overwritten.
- Upload files with identical names from different users and check they don't collide in storage.
- Check the stored filename and metadata survive unusual characters and long names without truncation or encoding problems.
- Check the audit log is append-only and tamper-evident. A user shouldn't be able to edit or delete entries, and timestamps should come from the server clock in a consistent timezone.
- Check backups and restores preserve the file, its metadata and the access permissions.
- Check the file isn't silently modified, such as by metadata stripping, recompression or virus-scanner "cleaning", without being recorded.

## Security

**Access control (the key acceptance criterion)**
- After upload, user B (another paralegal in the same firm) cannot see, list, search, download or preview user A's document.
- Test an admin, a manager and a user from another tenant or firm. Expected access should follow the rules and be documented.
- Try direct object reference attacks (IDOR): guess or increment the document ID or URL in the UI, API and download links.
- Test unauthenticated access to the download URL, and a direct storage URL (an S3 or blob link) that bypasses the app.
- If the download links are pre-signed, test expiry, reuse and sharing the link.
- Check that search, thumbnails, previews, caches, CDN and email notifications don't leak the document's existence or content.
- Check that revoking access, deleting the user or changing roles takes effect immediately.
- Check the "only the uploader" default holds even if the sharing feature is used later (sharing must be an explicit action).

**Malicious uploads**
- Upload an EICAR test file, and malware inside a DOCX or PDF (macro, embedded JavaScript, launch actions). Check the file is scanned and quarantined, and the failure is audited.
- Upload an HTML or SVG file renamed to `.txt` containing a script, to test stored XSS when it is previewed or served.
- Test path traversal in filenames (`../../etc/passwd`, `..\..\`, null bytes `file.pdf%00.exe`).
- Test filenames containing SQL injection, script tags, or shell metacharacters, and check they are handled safely in the UI, the logs and the audit view.
- Upload zip bombs or decompression bombs (a tiny DOCX that expands massively, since DOCX is a ZIP) and XML bombs / XXE in DOCX XML.
- Test the denial-of-service angle: many simultaneous large uploads, slow-upload (slowloris-style) attacks, and rate limiting per user.
- Test MIME sniffing: the served `Content-Type` and `X-Content-Type-Options: nosniff`, and `Content-Disposition` on download.
- Check that uploaded files are stored outside the web root and are never executed.

**Transport, authentication and session**
- Check upload and download use HTTPS only, with no downgrade to HTTP.
- Check the upload endpoint rejects requests with a missing, expired, tampered or other user's token, and test CSRF on the upload request.
- Check session expiry during a long upload, and that a logged-out user can't complete an upload.
- Check encryption at rest, key handling, and that the file's contents never appear in logs or error messages.
- Check error messages don't leak server paths, stack traces or the existence of other users' files.
- Check that metadata such as author and GPS data inside files doesn't leak to other users unintentionally.

**Privacy and compliance**
- Check the audit log doesn't store file contents or sensitive data in plain text, and that access to the audit log is itself restricted.
- Check legal-hold and retention expectations: deleted files are really removed (or retained) as specified, including from backups and caches.

## Questions for the team

These are gaps in the story that could hide risk:
1. Who can see the audit report (the uploader, an administrator)?
2. Is virus scanning required, and is the file available before the scan finishes?
3. What happens on a duplicate filename?
4. How should the system behave if the audit write fails?
5. Is 20MB per file or per upload request?
6. What does "secure" mean here: encryption at rest and in transit, malware scanning, or both?
